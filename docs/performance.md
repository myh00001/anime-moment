# 架构与性能说明

## 一帧的处理链

USB V4L2 采集线程持续获取最新帧。调度器最多保留两帧在途；每个推理进程有独立的模型和人脸状态，目前各使用6个OpenCV线程，处理输入长边最多1280，当前输出默认最高长边1920（此前实验默认960，以下按各组明确尺寸比较）。生成场景后检测至多三个人脸，各人脸依次执行结构生成、动漫化和语义解析，再进行当前帧的五官比例、眉毛、皮肤、边缘融合处理。

默认在前一帧最后一个人脸的结构模型返回后，允许后一帧开始场景推理，填补各模型间CPU准备数据时的空档。两帧主推理链允许受控交错，最多两个输入在途。无人脸时在检测完成后允许下一帧；异常路径在完成或报错时释放调度。异常分割面积可能触发额外解析。不会无限累积模型任务。

两个独立进程避免同一 Python 解释器内原生推理与 CPU 工作相互等待。单纯开启两个 Python 线程虽然提高吞吐，但实验中会显著增加单帧延迟，因此没有用于最终方案。

输出按摄像头帧序号递增，过时的乱序结果不显示。GTK 每40ms检查一次新结果，只有结果变化才重绘；显示刷新频率不算模型 FPS。FPS是最近3秒真实完成并交付输出的速率，不是采集帧率。流水线有阶段重叠，因此总吞吐不等于平均单帧延迟的简单倒数。

## 2026-10-22 板端实验

- 固定单人样本：原 INT16 模型串行约1.50FPS、658ms；混合精度+受控双进程约2.31FPS、579ms，BPU采样平均90.84%。
- 正式流水线，四种已保存的单人姿态，40帧回归：约2.326FPS、平均585ms，BPU采样平均76.17%。不同输入和采样时刻影响占用读数。
- 四种姿态流水线输出与同一加速模型串行输出逐像素一致。相对旧INT16模型，完整画面的平均绝对像素差约0.204～0.687/255；七种人脸主模型裁剪输出平均差约4.14～5.39/255。不能把量化后输出描述为与旧模型完全相同。
- 当时现场 USB 镜头没有检测到人脸，输出960×540约9.8～10.4FPS、BPU约32%～42%、SoC约47～48°C。有人脸的2.33FPS是保存样本回归结果，并非用户此刻现场转头的测量。

模型原生尺寸、人物数量、CPU后处理、USB曝光、摄像头实际交付帧率和热状态都会影响速度。优先选择设备最高分辨率不一定能同时取得最高帧率。BPU利用率低可能是没有执行人脸模型或CPU成为瓶颈，不能直接由其百分比换算峰值TOPS。

## 排查

### 同日第二轮：更早释放调度

相同四姿态40帧，模型权重、量化版本和图像处理参数均未改变；另一个线程每0.5秒读取资源计数。

|下一帧启动条件|输出FPS|平均单帧延迟|P95延迟|平均BPU读数|
|---|---:|---:|---:|---:|
|上一帧最后人脸解析完成，旧默认|2.322|585.7ms|589.6ms|73.1%|
|最后人脸动漫模型完成|2.411|647.2ms|649.5ms|72.6%|
|最后人脸结构模型完成，新默认|2.779|641.8ms|644.4ms|88.3%|
|不按模型阶段限制，两帧持续并发|2.433|836.0ms|840.9ms|75.9%|

采用结构模型返回后启动下一帧，吞吐提高约19.7%，代价是平均单帧延迟增加约56ms。四组输出均与当前模型串行对应输出逐像素一致。BPU读数是瞬时忙碌状态的抽样平均，仍会随场景和CPU准备工作波动，不能保证恒定100%。

### 屏幕和采集设置验证

- GTK自身离屏窗口验证1280×720横屏和540×960竖屏，画面四角无黑边，设置面板可展开，小屏幕可滚动。
- 实际设置控件的分辨率、旋转、镜像值可保存和恢复默认；动态推理依次切换四组设置，每组6帧，输出尺寸与该组设置一致，输出与同设置串行计算逐像素一致。
- 设置变更时丢弃之前已在途的旧设置结果；FPS统计在第一帧新设置结果到来时重置，避免混合不同分辨率状态。
- 设置只改变应用采集后的旋转/裁剪与生成输出，不更改USB设备原生协商模式。摄像头仍优先最高分辨率采集。

### 输出分辨率与取景解耦修复

后续发现早期设置版会先按目标输出宽高裁剪原画，再按窗口比例裁剪显示。改变输出比例时可能因此意外放大。当前版本取消输入端按输出尺寸裁剪，分辨率以“输出长边”设置，实际宽高自动保持旋转后摄像头比例。只在显示时按窗口比例裁剪一次。

同一长边下，历史设置960×540、960×960、540×960在未旋转的16:9摄像头上均保持完整原始取景并实际输出960×540，避免旧配置重新引入变焦。四种长边在横屏和竖屏窗口内的归一化可见范围已做回归检查。旋转和镜像功能保留。

### 1920×1080 默认输出与精确CPU优化

默认值与“恢复默认”改为1920长边；本次部署同时将板上保存的输出迁移到1920×1080，保留旋转和镜像。API和网页的新默认也为1920。后续手动调低并保存的设置仍会保留，不在每次启动时强制覆盖用户选择。

四种保存的人脸姿态统一到1920×1080输入，模拟完整高清传帧负载；每组32帧，预热后统计：

|同为1920×1080|优化前|最终优化|
|---|---:|---:|
|真实完成输出|2.239FPS|2.353FPS|
|平均单帧处理延迟|880.1ms|792.4ms|
|BPU瞬时值抽样平均|65.9%|66.6%|
|相对旧版像素误差|—|最大0|

该组吞吐约提高5.1%，延迟约降低10%。BPU平均读数没有显著上升，不能称为稳定满载；现场有人脸读数可瞬时达到100%，仍随CPU准备和后处理阶段波动。不能将本组1080p帧率与此前960×540帧率直接作提速对比。

采用的改动：

- LAB色度加权改用OpenCV的CV_32F向量计算，最后再转uint8截断，保留原计算结果；仅对Canny非零边缘像素做轮廓加深。四姿态CPU收尾约203～211ms降到112～120ms，逐像素一致。
- 像素归一化、反归一化复用自有浮点输出缓冲，避免多份全分辨率临时图像；连续/非连续数组的算术均与原式严格比较。
- 锐化复用同一float32缓冲；未开启历史处理时不再复制无用的前帧。锐度诊断改在原输入尺寸计算，不为诊断放大整幅输入；生成画面不受影响。
- 保留双进程、4个OpenCV线程与结构模型完成后的放行时机。额外比较过共享内存（约2.32FPS）、三工作进程（约2.32FPS）及减少CPU线程（约2.25FPS），未比选定方案更好，因此不部署。

模型和量化版本均未更换。板端回归输出逐像素一致；保持完整取景、横竖屏铺满、输出比例自动匹配、手动关闭后不自动重开。每轮完成验证后提交并推送GitHub。

### 两小时追加实验：先排除退化方案

以1920×1080、四个单人姿态、每组40帧比较。首尾各测一次正式版本，分别2.430与2.429FPS。候选使用相同模型与精确亮度查表、就地锐化；所有候选最大像素差为0。

|候选调度|FPS|平均处理延迟|
|---|---:|---:|
|正式版本，结构阶段放行|2.430|776.6ms|
|查表候选，结构阶段放行|2.412|754.9ms|
|查表候选，无阶段限制|2.140|942.3ms|
|查表候选，动漫阶段放行|2.348|743.6ms|
|查表候选，解析阶段放行|2.184|696.1ms|

该轮没有可靠吞吐提升，因此没有修改正式调度。更低延迟或更高BPU占用不能代替FPS提升。线程数和优先级的后续筛选中，6线程查表候选达到2.483FPS，同轮基准首尾约2.355FPS；这只是短测候选，需要更长交替复测后再决定部署。

新增 `scripts/benchmark_pipeline.py`，可用用户自己保存在板端的图片重复测量真实流水线吞吐、延迟、BPU均值，并逐帧比较串行参考。工具仅保存数值报告，不保存图片或输入路径。测量期间应手动停用显示服务，结束后恢复；避免两个程序同时推理造成资源争抢。输入应保持原有摄像头尺寸，跨版本比较必须使用相同输入和输出设置。

```bash
systemctl --user stop anime-local-display.service
python3 scripts/benchmark_pipeline.py --service-dir service --edge 1920 \
  --frames 96 --report /tmp/benchmark-report.json /path/to/local-input.jpg
systemctl --user start anime-local-display.service
```

|顺序|版本|FPS|平均延迟|BPU采样均值|
|---|---|---:|---:|---:|
|1|原4线程|2.415|779.2ms|76.9%|
|2|查表与6线程|2.483|739.3ms|73.2%|
|3|查表与6线程重复|2.460|741.2ms|77.4%|
|4|原4线程重复|2.431|775.8ms|69.5%|
|5|查表与5线程|2.448|744.9ms|67.3%|
|6|查表与4线程|2.426|754.9ms|73.6%|

以首尾基准与两次候选的均值计算，吞吐约提高2%，延迟约减少4.8%。所有帧最大像素差为0；不会将短测最高值当作持续现场帧率。BPU读数仍明显波动，该方案不能称为BPU稳定满载。

本轮部署了6线程、就地锐化以及亮度直方图/查表。亮度源值仅有256种，先对256值计算原float32表达式，再应用LUT，避免每帧执行大量重复浮点运算；原滤镜、模型、五官和眉毛参数未变。新增亮度回归覆盖全部256个输入值及55组亮度边界。额外串行对照单人约683→642ms，无人约241→206ms，竖幅约700→649ms；四个单人姿态、无人、双人和竖幅均逐像素一致。双人测试输入为1920×540，并非1080p双人帧率。

正式显示程序已恢复，最高输出、全屏、镜像和`Restart=no`保持不变。脱敏数值记录见 [benchmarks/2026-10-22-round2.json](benchmarks/2026-10-22-round2.json)，不包含采集画面。

### 精确原生CPU运算与场景阶段调度（2026-10-23已部署）

以C循环完成最终锐化和LAB四分之一权重合成，使用2个OpenMP线程，保留每一步float32计算顺序并禁止FMA及fast-math。合成的整数运算与原浮点截断完全一致。CPU收尾缩短后，将下一帧放行时机提前到当前帧场景模型返回，仍保持双进程、最多两帧在途和最新输入。

最终公开代码使用独立进程进行144帧ABBA对照，前8帧预热，四个单人姿态，1920×1080输出：

|顺序|方案|FPS|平均延迟|BPU采样均值|
|---|---|---:|---:|---:|
|1|此前正式版|2.571|714.1ms|72.9%|
|2|原生运算与场景调度|2.760|702.5ms|77.0%|
|3|候选重复|2.758|702.3ms|81.6%|
|4|此前正式版重复|2.603|712.9ms|81.7%|

平均吞吐提高约6.7%，延迟减少约1.6%。全部576帧最大像素差为0；另对四种单人姿态、无人、双人和竖幅输入逐像素回归，全部一致。没有更换模型或风格参数。完全取消阶段门控在长测中退化至2.35～2.40FPS，已放弃；未采用只凭BPU占用更高的配置。

部署后无人现场输出约7.9～8.5FPS，不能视为有人脸的帧率。确认1920×1080、全屏、镜像、场景阶段放行，无近期推理错误；手动关闭后保持关闭、自启动仍启用。当前BPU采样不足以证明持续满载。

运行 `bash scripts/build_native.sh` 在目标Linux设备编译可选库。构建使用临时文件再重命名，避免覆盖正在映射的库；更新后需要重新启动程序。没有库时回退原算术与结构阶段门控。算术测试覆盖百万随机float32值、奇数长度、并行阈值及所有uint8合成输入对。数值记录见 [benchmarks/2026-10-23-native.json](benchmarks/2026-10-23-native.json)。

### 当前模型耗时与并发边界

暂停显示后，对当前四个HBM分别执行10次单线程官方运行时剖析：结构模型约242.94ms BPU、解析约64.17ms BPU和0.27ms CPU、场景约33.30ms BPU、动漫约10.95ms BPU。结构模型全部在BPU执行，占主要耗时；此前CPU ReduceMean版本的旧报告不适用于当前权重。单人每帧四模型BPU任务耗时之和约351.4ms，对应约2.85FPS的串行任务上限，已经接近当前2.76FPS。此估算不等于硬件算术单元100%利用率，监控百分比仍可能更低。

三工作进程候选触发运行时停滞，正式程序未采用。已通过板卡正常重启恢复原双进程、全屏及镜像，恢复后输出正常；本轮不再尝试三运行时并发。后续重点验证精确CPU后处理优化和更低延迟，保留全部模型及画质。数值见[模型剖析记录](benchmarks/2026-10-23-model-profile.json)。
